# koishi-plugin-image-prompt

[![npm](https://img.shields.io/npm/v/koishi-plugin-image-prompt?style=flat-square)](https://www.npmjs.com/package/koishi-plugin-image-prompt)

🎯 **一键将图片转换为手办风格！**

基于 OpenAI 兼容的 Chat Completions 接口，支持多种 AI 绘图模型，让你的图片瞬间变成精美手办。

**特色能力**：参考图片分组 + AI 按需选图 · 两级检索选图 · 多模态识图还原 · 用户附加需求融合进提示词 ·
提示词回显（QQ 走 markdown 代码块）· 文字渲染参考图防中文崩字 · 生成结果自动入库形成闭环 ·
后台绘图 + 完成推送 · 参考图描述 AI 自动生成 · 429/限流自动退避重试。

## ⚙️ 插件设置

直接在 Koishi 控制台的插件设置中填写「API 设置」即可：

| 配置项 | 说明 | 默认值 |
|---|---|---|
| API 服务器地址（baseUrl） | OpenAI 兼容的 Chat Completions 接口地址 | `https://api.gptgod.online/v1/chat/completions` |
| 使用的模型（model） | 生成图片所使用的模型名称 | `gemini-2.5-flash-image` |
| API 密钥（apiKey） | 你的 API Key（请求会携带 `Authorization: Bearer <key>`） | 空 |
| 最大重试次数 | 请求失败后的最大重试次数 | 3 |
| 重试间隔(毫秒) | 每次重试之间的等待时间 | 1000 |

建议前往[gptgod](https://gptgod.online/register/n7iydg8nf09ghbikik3jytod)获取你的api key

> 注意：请填写支持图片输入（vision / image）的模型，否则无法正常生成图片。

## 🖼️ AI 选择参考图片

参考图片不再只是「一堆链接」，而是以**分组**的方式注册，由 AI 按需挑选。

### 1. 注册参考图片组

在插件配置 → **参考图片组** 中新增分组：

| 字段 | 说明 |
|---|---|
| 组名称 | 在指令中通过该名称引用，例如 `角色A` |
| 是否启用 | 关闭后不再参与 AI 挑选 |
| 图片链接 | 参考图的 URL |
| 图片描述 | **关键**：告诉 AI 这张图是什么、适合什么用途，AI 只依据描述来选图 |

### 2. 在指令中引用组

在指令配置中找到该指令，填写：

| 指令配置项 | 说明 |
|---|---|
| 引用的参考图片组名称 | 可填多个组名，AI 会从这些组的全部图片中挑选 |
| 启用 AI 智能选择参考图片 | 关闭则该指令不调用选图模型 |
| AI 最多为该指令选择的参考图片数量 | **0 = 跟随全局设置**（全局在「AI 选图设置 → 默认最多选择的参考图片数量」） | 0 |
| 缺少合适参考图时询问用户补充发送 | 关闭则不再追问用户 |

> 指令留空组名时，是否使用全部组由「AI 选图设置 → 指令未指定组时使用全部组」决定（默认开启）。
> 未配置任何参考图片组的指令不会触发选图请求，行为与之前完全一致。

### 🔍 选图是怎么挑的（打分制）

以前的做法是「把几十张候选图一次性塞给模型，让它挑」。问题是**模型没有退路**——
哪怕图库里一张都不合适，它也必须从里面挑一张出来交差，于是就有了「乱选图」：

- 选了完全不相关的图
- 明摆着没有合适的图，还是硬凑一张
- 一次挑回好几张高度重复的图
- 真正该选的那张反而落选

现在的流程参考了 **NeoBot 的「先检索、再引用」** 思路，把「挑图」拆成四步：

```
① 需求分析   只给指令和用户需求，**不给任何候选图**
             → 模型只能老实说清「这次画面上要什么」（主体/硬性要素/加分要素/不要什么）
             → 它根本没有「可挑的对象」，也就不可能乱选
                    ↓
② 关键词召回  拿①的要素在本地做文本匹配，把候选池从几十张缩到十几张
             → 纯本地计算，不花请求；描述写得好这里就准
                    ↓
③ 逐图打分   把这十几张交给模型，要求给**每一张**打 0-100 分
             → 硬性要素缺失 → 只能给 0-30 分
             → 描述为空 / 看不懂 → 一律 0 分（不许猜）
             → 拿不准就打低分（宁可漏选，不可乱选）
                    ↓
④ 阈值兜底   低于「最低分数线」（默认 60）的一律丢弃
             → 一张都不达标 → 如实说「图库里没有合适的参考图」+ 原因（最高多少分）
               并（若开启询问）请用户补发一张参考图
             → **绝不**把候选全塞进去当参考
```

几个附带的好处：

- **每次选图都有据可查**：日志里会打 `逐图打分（阈值 60）：最高 92 分，达标 2 张，选中 1 张 | 1:92分(命中白发双马尾) …`
- **不用再靠「调提示词」救**：以前乱选只能反复改提示词，现在阈值是硬约束，调不动就是不给过
- 用户说「**随意画 / 自由发挥 / 别参考**」会直接跳过选图（可通过「用户说不用参考时跳过选图」关掉）
- 描述完全相同的重复图会自动合并

> **关键前提：参考图的描述必须写。** 打分制下「描述为空」的图一律 0 分，永远不会被选中。
> 描述只写「一个女孩」这类泛泛的话，也基本拿不到 60 分。想让选图准，就把描述写具体
> （发色发型、服装、动作、画风），或者用 `生成描述` 指令让识图模型自动写。

> **一张都没达标时不会硬凑。** 本插件是**参考图驱动**的——手里一张参考图都没有就没办法开画，
> 所以这时插件的做法是「如实告知 + 请你补发一张」，而不是随便抓一张不相关的图交差。
> 提示里会带上打分详情（例如「图库里没有合适的参考图：没有图达到 60 分门槛（最高只有 32 分）」），
> 方便你判断是**该给图库补图**还是**该调低分数线**。

想回到旧行为：把「选图模式」改成 `旧版` 即可（会同时启用下面的「两级检索」开关）。

### 4. 交互流程

1. 用户触发指令（可附带文字说明，自定义指令的文字会并入绘图提示词，同时也作为选图依据）。
2. **打分制**：先做需求分析（不给候选图）→ 本地关键词召回 → 逐图显式打分 → 分数达标的才入选。
   旧版：把候选图片的「编号 + 所属组 + 描述」一次性交给模型，返回 `{"selected":[编号], ...}`。
3. 若模型判定缺少合适的参考图（`needUserImage: true`），插件把 `askMessage` 发给用户，等待用户发送图片；
   用户发送的图片会被直接使用，若附带文字说明则再选一次。
4. **一张都不达标时**（打分制）：如实告诉用户「图库里没有合适的参考图」并给出打分原因，
   不会拿不相关的图硬凑；开了「缺少合适参考图时询问用户补充发送」的话会先请用户补一张参考图。
5. 选中的参考图 + 用户图片一起提交给绘图模型。
6. **AI 选中的参考图也算数**：指令要求的图片数量（maxImages）会把 AI 选中的图计入，
   已经够了就不再追问用户发图（例如「手办化」要 1 张图，AI 选中 1 张后直接开画）。
7. 选图**报错**时（走不通/超时，与「没有合适的图」是两回事）：开启「回退」则使用候选池内全部图片；
   关闭（默认）则本次不带参考图，并在处理提示里说明选图未生效及原因。

### 📝 提示词回显

处理时会把**最终优化后的提示词**一起发出来，方便你确认 AI 到底用了什么（含识图模式追加的「参考图关键特征」）。

| 配置项 | 说明 | 默认 |
|---|---|---|
| 发送优化后的提示词 | 关闭则不回显 | 开 |
| 回显提示词的最大字符数 | 超出截断并标注；**0 = 不截断** | 4000 |

- **官方 QQ**（`qq` / `qq-*` / `qqbot`）：发 `markdown` **元素**，由适配器走 QQ 的 markdown API，
  客户端渲染成代码块
- **其它平台**（QQ 频道、OneBot 系、Discord、Telegram、KOOK…）：纯文本

> **代码块围栏必须独占一行**：适配器是把 markdown 内容直接拼在已有文本后面的，中间不补换行。
> 所以提示词会**单独作为一条消息**发送，且内容前补一个换行——否则围栏会被前文顶到行中，
> QQ 不会识别成代码块（提示词按普通 markdown 渲染，末尾那个围栏反而开出一个空代码块）。
>
> 回显会**保留提示词的原始换行**（不压成一行），代码块里段落结构才看得清。
> 内置指令的提示词普遍上千字符（「手办化」就有 1463 字符），默认上限 4000 刚好能完整显示；
> 自定义指令的提示词如果更长，把它设为 0 不截断，或调大到 20000。
> QQ 的 markdown 有内容长度上限，太长可能被拒收，那时再调小或关掉回显。
>
> **关键点**：光在字符串里写 ``` 是没用的，客户端只会当普通文本原样显示。
> 必须构造 `h('markdown', content)` 元素，让适配器走专门的 markdown 接口
> （`koishi-plugin-adapter-qq-crack` 里 `type === 'markdown'` 分支负责这件事）。
>
> 平台白名单只认官方 QQ，**`qqguild`（频道）不支持**——它走另一套编码器，
> md 元素在那里会被当纯文本原样发出去。口径与 kkk 插件的 `supportsMarkdown` 一致。

### ♻️ 生成结果入库（闭环）

画完的图自动存进图库，下次能被自己检索到并复用——对应 NeoBot 的 Gallery。

| 配置项 | 说明 | 默认 |
|---|---|---|
| 把生成结果自动存入图库 | 总开关 | 关 |
| 存入哪个参考图片组 | 不存在会自动创建 | 生成结果 |
| 用什么当描述 | 完整提示词 / 用户附加需求 / 两者拼接 | 完整提示词 |
| 描述截断长度 | 提示词通常很长 | 120 |
| 图库容量上限 | 超出淘汰最旧的 | 50 |
| 图库指令名 | 查看/清空 | 图库 |

指令：

```
图库           列出入库的图片（最多 20 条）
图库 角色A      只列名字/描述含「角色A」的
图库 清空       清空图库
```

> **检索到它的前提**：对应指令的「引用的参考图片组名称」里包含这个组名，
> 或者「指令未指定组时使用全部组」是开启的（默认开）。
>
> **为什么不在控制台里显示**：入库走本地文件 `data/image-prompt/gallery.json`，
> 而不是写回插件配置——写回配置会触发插件**重启**（`scope.update(config, true)` 的行为），
> 每画一张图重启一次太脏。好处是不重启、重启 Koishi 后也还在。

### 💬 随指令发的需求会写进提示词

```
手办化 deepseekQ版 在偷吃白饭被发现的表情
```

这句里的附加需求会**同时**用于两件事：

1. 交给 AI 选图（按「deepseekQ版」等关键词去参考图组里挑图）
2. **并入绘图提示词**（追加在系统提示词末尾，用空行分隔）——这样出图才会带上「偷吃白饭被发现的表情」

> 之前只有 `custom` 类型的指令才合并用户输入，普通指令（手办化、coser化…）只拿它去选图、
> 画图时丢掉，所以会出现「图选对了但需求没体现」。现在两者都合并。
>
> 另外文本取的是**指令参数**，不是整条消息——否则提示词里会混进指令名（「手办化 xxx」→ 只取 xxx）。

### 🪄 提示词融合方式

| 配置项 | 说明 | 默认 |
|---|---|---|
| 附加需求如何并入提示词 | `rewrite` 融合重写 / `merge` 直接追加 / `off` 不处理 | `rewrite` |
| 把用户附加需求并入提示词 | 关闭则只用于选图，不改提示词 | 开 |
| 融合重写用的提示词模板 | 占位符 `{prompt}` 原始提示词、`{userInput}` 用户附加需求 | 内置模板 |

- **rewrite（融合重写，推荐）**：让模型把需求写进提示词**该去的位置**（表情/动作/神态/服装/场景），
  而不是贴在最后。模板要求它**保留原始提示词的全部细节、不得删减**，语言与原文一致
- **merge（直接追加）**：把需求贴在原始提示词末尾，不做改写
- **off**：只用指令自身的提示词，需求仅用于选图

rewrite 失败时自动退回 merge 的结果，不会因为优化失败而不出图；失败会在处理消息里提示
「（提示词融合失败，已改为追加模式）」，方便排查（多半是模型限流或返回被判空）。
用的是 AI 选图那套接口/模型（想换更强的模型可以单独给「AI 选图设置」换模型）。

> **选图数量**：指令里的「最多选择的参考图片数量」默认 0 表示跟随**全局**设置。
> 想一次选 5 张，改全局那个即可（指令级留 0）；指令级填了具体数字则以指令级为准。

> **多张参考图 = 画面编排**：开启识图且选中多张图时，模型给出的是一段**分镜式的画面编排**
> （各角色位置、姿态、互动与视线关系、共同场景氛围、各自外形特征），而不是逐张罗列特征，
> 这样多角色同框的图才不会各画各的。提示词里对应段落标题是「画面编排（务必还原）」。

### 🈶 文字渲染参考图（解决中文崩字）

绘图模型画中文十有八九是错字、乱码。与其让它「自己写」，不如**先让浏览器把文字渲染成一张图**，
连着参考图一起发过去，让它照着抄字形。

```
渲染文字 我早就发现你偷吃了      手动渲染（会回一张图，随后 N 秒内的绘图自动带上它）
画图 两个 AI 娘在吵架，要有台词    选图模型自己写台词 → 自动渲染 → 并入绘图参考图
```

**文字从哪来**（三档，取第一个命中的）：

1. **选图模型自己写**（推荐）：选图提示词会要求模型判断画面上要不要出现文字，要的话写进
   JSON 的 `text` 字段（每行一句，用 `\n` 换行，每句不超过 30 字）。你说「画两个 AI 娘吵架」，
   它会把对白写出来，插件再渲染成图。不需要文字时它留空，就不会多渲一张图。
2. **手动指令**：`渲染文字 xxx`，最明确，优先级最高。
3. **正则兜底**：从提示词/你的输入里抓「」`“”`《》【】和「台词：」后面的中文（选图没开时走这条）。

渲染出来的图**只发给绘图模型**——选图模型自己知道写了什么，不需要再发回去浪费 token。

| 配置项 | 说明 | 默认 |
|---|---|---|

识别到的文字会以「换行」拼成一块渲染（多行 = 多行台词），并在提示词末尾追加一句
「文字必须与文字参考图完全一致，不得自行编造字形」——模型才会真的去抄。

> 渲染用的是工作区里已启用的浏览器服务（`koishi-plugin-puppeteer` 或
> `@shangxueink/koishi-plugin-puppeteer-without-canvas`）。服务不可用时只会记一条警告，
> 绘图照常走，不会因为渲染失败而画不出来。

### ⚡ 后台绘图（不阻塞）

出图常常要几十秒，同步等待时消息一直转圈。开启后：先回「已开始后台绘图，画好后会通知你」，
出图在后台跑，完成后**主动推送**结果（带引用回复）。

| 配置项 | 说明 | 默认 |
|---|---|---|
| 后台绘图 | 总开关 | 关 |
| 同时进行的任务上限 | 超出的排队，逐个执行 | 3 |
| 排队时提示 | 告知前面还有几个任务 | 开 |

失败也会推送失败消息。插件停用时后台任务自动跳过。

### ✍️ 自动生成参考图描述（不用再手填）

描述是选图和检索的唯一依据，一张张手填很痛苦。用指令让模型自己看图写：

```
生成描述            为所有启用组里「描述为空」的图片生成描述（一次最多 8 张）
生成描述 角色A       只处理名字含「角色A」的组
生成描述 + 发一张图  只识别这张图并返回描述，方便自己复制
```

生成的描述会**自动写回插件配置**（控制台里能看到），同时把结果发给你。

| 配置项 | 说明 | 默认 |
|---|---|---|
| 自动生成描述的指令名 | 挂在指令根下 | 生成描述 |
| 生成描述用的模型 | 留空则用选图模型；**必须是支持图片输入的模型** | 空 |
| 生成描述的提示词 | 要求模型写出便于检索的关键词 | 内置模板 |
| 一次最多处理多少张 | 避免请求过多被限流 | 8 |

> 提示词默认要求模型写出「红发双马尾」「白色水手服」这类**具体词**，而不是「一个女孩」，
> 这样两级检索才召回得准。默认模型 `Qwen/Qwen2.5-7B-Instruct` 是纯文本模型，
> 用它生成描述会失败——请换成 VL 模型或单独填写「生成描述用的模型」。

### 🔍 两级检索选图（参考图很多时必开）

参考 NeoBot「自己找图自己画」的思路：**不要让模型一次看完整个图库**。

| 配置项 | 说明 | 默认值 |
|---|---|---|
| 两级检索选图 | 关键词召回 → 精排 | `true` |
| 候选超过多少张才启用两级 | 少于此值直接一次问完，反而更快 | 12 |
| 第一级召回数量上限 | 精排只看这么多张 | 12 |
| 检索提示词模板 | 占位符 `{index}` `{userInput}` `{command}` `{prompt}` `{topK}` | 内置模板 |

流程：

1. **召回**：模型先读一遍「编号 + 组名 + 描述」的纯文本索引，输出 3-6 个检索关键词 + 直接看中的编号；
   插件拿关键词在**全部**候选里做本地文本匹配（中文子串 + 2-gram 部分命中），两者合并去重取 Top K。
2. **精排**：只把这 K 张交给模型最终挑选。识图模式下也只有这几张需要真的发图片，
   token 和耗时都大幅下降——图库从 20 张涨到 200 张，精排这一次的开销几乎不变。
3. 关键词一个都没命中时，自动退回「一次性全量问」的老路径，不会因此选不到图。

处理提示里会回显检索效果：`（参考图检索：48 张中命中 9 张候选）`。

> 想让召回更准，就把图片描述写成**描述里真的会出现**的词
> （NeoBot 图库也是这么建议的：同一角色的多张立绘保持用词一致，例如都写「红发双马尾」「白色水手服」）。

### 👁️ 识别图片（多模态）

默认只把「编号 + 描述」发给选图模型，模型是**盲选**。若你的选图模型支持看图（VL / 多模态），
勾选 **「选图模型支持识别图片（多模态/VL）」**，插件会按 `[1] 描述` → 图片 → `[2] 描述` → 图片 …
的顺序把候选图片本身一起发过去，模型对着真实图片挑选，准确率明显更高。

- 图片以 `image_url` 形式发送，**链接必须能被模型服务端访问**（公网直链，不能是需要登录或防盗链的图床）
- 「最多附带多少张候选图片」默认 6 张，超出部分仍发文字描述（避免请求体过大/超时）
- 带图片请求失败（模型不支持、图片取不到）会自动退回纯文字再试一次，可用
  「带图片请求失败时退回纯文字再试一次」关闭
- 识图模式下模型会额外输出 `hint`（它看到的发型、服装、配色、姿态、画风等关键特征），
  插件把它并入绘图提示词：`参考图关键特征（务必还原）：…`，出图更还原参考图。
  不需要可在「把模型看图后给出的关键视觉特征并入绘图提示词」里关掉

**已知不支持识图的模型**（开启后会被服务端拒绝，返回 400）：

- **DeepSeek 全系**（`deepseek-chat` / `deepseek-reasoner` 等）：纯文本模型，不支持图片输入
- `Qwen/Qwen2.5-7B-Instruct` 等 `-Instruct` 纯文本模型

支持识图的模型（示例）：`Qwen/Qwen2.5-VL-72B-Instruct`、`gemini-2.5-flash`、
`gpt-4o-mini` 等标注 vision / 多模态的模型。

> 带图片请求失败时插件会自动退回纯文字重试，并在日志里提示
> 「若该模型不支持图片输入（DeepSeek 等纯文本模型会返回 400），请关闭『选图模型支持识别图片』」。

### 🔁 限流（429）处理

选图模型和绘图模型走的是同一类接口，免费额度下很容易撞上 `429 Too Many Requests`。插件的处理策略：

1. 识别 429 / 503，优先按响应头的 `Retry-After` 等待；没有该头则指数退避
   （基础间隔 3 秒 → 6 秒 → 12 秒，上限 30 秒）。
2. 单次等待超过「单次重试最长等待时间」（默认 20 秒）就不再重试，直接按失败处理，避免用户干等。
3. 失败后在处理提示里给出人话原因，例如：`AI 选图失败（被限流（429 Too Many Requests）），本次不使用参考图片`。

遇到频繁 429 的几种处理方式：

- 调大「重试基础间隔」与「请求失败重试次数」，或放宽「单次重试最长等待时间」

### 📮 QQ 官方机器人的「被动回复」限制（40034128）

报错 `回复消息失败，被动回复时间或者次数超过限制`：QQ 官方机器人里，**引用一条用户消息 = 被动回复**，
有 **5 分钟时效 + 次数上限**。而一次绘图要发好几条消息（选图中 → 处理中 → 提示词回显 → 结果图），
每条都带引用必然超限。

⚠️ **关键坑：去掉引用元素并不等于变成主动消息。** `koishi-plugin-adapter-qq-crack` 内部是
`msg_id = session.messageId` —— 只要消息经过 `session.send()`，哪怕不带 `h.quote()`，
也会被当成被动回复并递增 `msg_seq`，照样受时效/次数限制。**真正的主动消息只能走
`bot.sendMessage(channelId, content, guildId)`（不经过 session）。**

插件现在按下面三条规则处理，不需要你管：

1. **同一条用户消息只引用一次**：第一条消息带引用（看起来是"回复你"），后续都是普通消息
2. **被动回复有次数预算**：同一条消息最多走 3 次被动回复，用满自动改走主动消息
3. **被动回复被拒时立刻降级**：捕获 40034128，改用 `bot.sendMessage` 发真正的主动消息

后台绘图最容易踩这个（出图要几分钟，早过时效了），完成通知同样会自动降级。

#### 再省一步：把提示合并成一条 markdown

默认开启「合并消息」后，「正在挑选参考图 / 正在处理 / 优化后的提示词」不再逐条发，
而是攒到最后**合成一条 markdown 消息**；结果图再用 `![](链接)` 单独发一条。
一次绘图从 4~6 条降到 **2 条**：

```
①  正在智能挑选参考图片...
    正在处理图片，请稍候...
    （已为你挑选参考图片：…）
    ```
    优化后的提示词（代码块）
    ```
②  ![](https://...图片链接)   ← 实际是 ![#400px #225px](链接)（自动按真实比例）
```

第 ① 条是**在开始画图之前**就发出去的（不会让你在绘图期间干等、以为卡住了）；
第 ② 条是图片出来后再发。

**关于结果图的两个坑：**

- **必须带尺寸**：QQ 官方语法是 `![#宽px #高px](url)`，**不带尺寸手机端 QQ 不渲染**。
  但**写死宽高会把非方形图拉伸变形**——所以插件默认开启「自动尺寸」：下载结果图读文件头
  （PNG/GIF/JPEG/WebP 都支持，不解码整张图），按真实比例等比缩放到「显示宽度上限」（默认 400px）。
  想手动指定就把「自动尺寸」关掉，再填「显示宽度 / 显示高度」（0 表示不限制）。
- **最好走一次 assets**：绘图接口给的虽然是公网链接，但手机端 QQ 经常拉不到（防盗链/域名）。
  开启后先经 assets 服务（`koishi-plugin-assets-qqbot-part-file` 等）转成平台可访问的地址；
  上传失败会自动用原链接，不会更差。

| 配置项 | 说明 | 默认 |
|---|---|---|
| 合并消息 | 把过程提示合并成一条 | 开 |
| 结果图用 markdown | 支持 markdown 的平台用 `![#Wpx #Hpx](url)` 发结果 | 开 |
| 结果图经 assets 上传 | 外链手机端常拉不到，转成平台地址 | 开 |
| 结果图自动尺寸 | 读真实宽高、等比缩放，避免非方形图被拉伸 | 开 |
| 显示宽度上限 | 自动尺寸时的最大宽度，高度按真实比例算 | 400 |
| 手动宽 / 高 | 仅在关掉自动尺寸时生效，0 表示不限制 | 0 / 0 |

细节：
- 需要你**立刻回应**的提示（等你发图、等自定义提示词）会先把攒着的消息发出去再问
- 合并后若超过 QQ markdown 单条长度上限，会自动把提示词代码块拆成第二条
- 关掉「合并消息」就回到逐条发送；不支持 markdown 的平台（频道、OneBot）自动用纯文本/普通图片消息

### 🩺 排查「AI 选图响应中没有文本内容」

这个报错的意思不是网络问题，而是**接口返回了 200，但插件从返回里取不出文字**。

#### 最常见原因：`max_tokens` 太小，被推理模型吃光

用 `deepseek-flash`（DeepSeek-V4.1-Flash）这类**推理模型**实测，附 6 张图选一次图：

```
max_tokens=1000  → finish_reason: length, content: "", reasoning_tokens: 1000   ❌ 全被思考吃掉
max_tokens=8000  → finish_reason: stop,   content: "{...}", reasoning_tokens: 2202  ✅
```

模型光思考就要 1000～4000 token，额度给小了，正文一个字都生成不出来，`content` 就是空的。
插件现在默认给到 **8000**（选图）/ **3000**（关键词）/ **8000**（提示词优化），
并且**检测到 `finish_reason=length` 会自动加大额度重试**，不用你手动调。

| 配置项 | 说明 | 默认 |
|---|---|---|
| 选图（精排）输出长度上限 | 太小会报「没有文本内容」 | 8000 |
| 关键词阶段输出长度上限 | 两级检索第一级 | 3000 |
| 提示词优化输出长度上限 | 融合/扩写 | 8000 |
| 截断后最多加大到 | 自动重试的上限 | 32000 |

#### 其它已自动兼容的情况

| 接口/模型的行为 | 处理方式 |
|---|---|
| 推理模型把正文放在 `reasoning_content` | 自动取 |
| 模型把回答混在 `<think>…</think>` 里 | 自动剥离，只留正式回答 |
| 输出长度参数只认 `max_completion_tokens`（o1/o3/gpt-5/reasoner） | 自动识别；失败时**重试会自动换另一个参数名** |
| 响应被 `max_tokens` 截断（`finish_reason=length`） | 明确报「被截断」并**自动加大额度重试**；此时绝不会把 `reasoning_content` 里没想完的思考过程当答案 |
| 命中安全策略（`content_filter`） | 明确报「被安全策略拦截」 |
| 中转站把结构塞进 `data` 里 / 返回 Anthropic 风格 `content` 数组 | 自动取 |
| 中转站无视 `stream` 直接回 SSE 流 | 自动拼接所有 `data:` 块 |

还是不行的话，用**诊断指令**（默认 `测试选图`，挂在指令根下）发一次真实请求，
它会回显接口地址、模型、用的长度参数名、取到的内容，取不到时把**原始返回**打出来：

```
测试选图
→ 接口：https://...
  模型：deepseek-v4.1-flash
  长度参数：max_tokens
  取不到内容：message.content 为空：{"id":"...","choices":[...]}
  原始返回：...
```

拿到原始返回就能判断是模型名写错、中转站格式另类，还是模型本身不支持 JSON 输出。
也可以在「AI 选图设置」里手动指定**输出长度参数名**。

### ❌ 不会重试的错误

`400 / 401 / 403 / 404 / 422` 这类属于永久性错误（参数错、密钥错、地址错、模型不存在），
重试多少次结果都一样，插件**只请求一次就放弃**，并把服务端返回的具体原因显示出来，例如：

- `请求被拒绝（400）：Model Not Exist` → 模型名写错了
- `鉴权失败（401）：Invalid API key` → 密钥不对
- `接口地址不存在（404）：Not Found` → baseUrl 写错了

只有 `429` 限流、`5xx` 服务端错误、超时/网络错误才会重试。
- 在「AI 选图设置」里单独填一个接口地址/密钥，与绘图接口分开（不复用额度）
- 换一个限流更宽松的对话模型（默认 `Qwen/Qwen2.5-7B-Instruct` 是免费模型，容易限流）
- 给不需要参考图的指令关掉「启用 AI 智能选择参考图片」，减少无效请求

## 🔧 常见问题

### Q: 提示生成失败
**A:** 检查 baseUrl 是否可访问、apiKey 是否正确、所用模型是否支持图片输入。

### Q: API 返回 401
**A:** 确认 apiKey 已正确填写，并且服务端允许 Bearer Token 鉴权。

### Q: API 返回 429 或配额不足
**A:** 检查账户额度，插件检测到配额不足会自动停止重试。

### Q: 启动报 `ReferenceError: Cannot access 'galleryLoaded' before initialization`
**A:** 这是 **1.0.4 及更早版本**的 bug，1.1.1 已修复，升级即可。

原因：图库启动预热 `void loadGallery()` 写在了 `let galleryLoaded = false` **之前**。
`loadGallery` 是 `async` 函数，函数体开头读 `galleryLoaded` 时变量还在「暂时性死区」，
于是抛出的 `ReferenceError` 变成了**未处理的 Promise 拒绝**，日志里显示为 `[W] app`：

```
[W] app ReferenceError: Cannot access 'galleryLoaded' before initialization
    at loadGallery (.../koishi-plugin-image-prompt/lib/index.js:1715:7)
```

它的表现是**图库/参考图检索静默失效**（后续报「两级检索未召回候选」「AI 选图失败」），
而不是让机器人起不来 —— 所以容易被当成别的问题排查。修法很简单：把预热调用挪到声明之后。

> 本仓库 `tests/apply-smoke.js` 就是专门防这个的：用真实 koishi Context 跑一遍
> `apply` + `ready`，监听 `unhandledRejection`。跑 `node tests/apply-smoke.js` 即可验证。
